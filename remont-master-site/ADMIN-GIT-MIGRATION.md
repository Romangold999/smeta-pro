# РемонтМастер — переход на GitHub-only и единая админка

Рабочая ветка: `remont-master-admin-git`.
Публичная ветка сайта: `remont-master-pages`.
Текущая опубликованная версия не меняется до прохождения проверок.

## Неподвижные требования

- Не использовать Cloudflare, внешние БД, облачные диски, стороннее файловое хранилище или платный сервер.
- GitHub — единственное хранилище исходников, данных, фотографий, каталога, статей, новостей и объявлений.
- GitHub Pages — публикация сайта и MAX Mini App из GitHub.
- Существующий дизайн, навигацию, калькулятор/каталог и поведение сохранять; не переписывать сайт с нуля.
- Админка — тот же сайт в режиме редактирования, отдельный адрес `/admin/`, контекстное редактирование элементов.
- Отдельный APK администратора открывает ту же веб-админку и работает с теми же данными.
- Никаких GitHub-токенов в публичном JS, HTML, APK или репозитории.
- Сначала тестовая ветка и проверка, затем публикация.

## Текущая техническая картина (проверено 2026-11-25)

- Сайт: `remont-master-site/index.html` (около 56 КБ).
- Каталог: `remont-master-site/work-catalog.js`.
- Клиентская синхронизация: `remont-master-site/client-api.js`.
- `remont-master-site/api-config.js` содержит адрес старого Cloudflare Worker.
- `client-api.js` запрашивает у Worker `/api/content`, `/api/catalog`, `/api/categories`, `/api/diy`, `/api/concrete`, `/api/media`, а также отправляет события `/api/analytics/pageview` и заявки `/api/leads`.
- В `client-api.js` уже есть генерация встроенного iframe-плеера для Rutube, YouTube и VK Video. При миграции сохранить её и отдельно проверить поведение Rutube iframe в MAX Mini App, в том числе fullscreen и ограничения встраивания.
- Поэтому Worker нельзя отключать до переноса всех используемых данных и проверки локальных резервных данных.
- В текущей ветке есть Android-проект `:app`, но отдельного `:admin-app` пока нет. Существующий workflow `android.yml` собирает Smeta Pro, а не APK админки РемонтМастер.
- Ветка Pages на момент проверки: последняя сборка успешно собрала сайт и загрузила Pages artifact размером около 501 КБ, но `actions/deploy-pages` получил ответ «Found 0 artifact(s)». Это ошибка этапа публикации, не ошибка HTML-сборки. Уникальное имя артефакта само по себе проблему не устранило.

## Безопасная модель админ-доступа без собственного сервера

GitHub Pages статический и не может проверять пароль на сервере или безопасно хранить секрет. Клиентский пароль сам по себе не защищает запись в репозиторий.

Рассматриваемый Git-only вариант: администратор явно вводит ограниченный Fine-grained Personal Access Token GitHub, выданный только для этого репозитория с минимальным разрешением Contents: Read and write. Токен:
- не встраивается в исходники, APK или данные сайта;
- не передаётся публичным посетителям;
- используется только в админ-сессии для GitHub Contents API;
- по умолчанию не сохраняется постоянно; выход очищает сессию.

Перед реализацией проверить ограничения GitHub API, CORS, загрузку бинарных изображений, обработку конфликтов SHA и безопасное поведение в MAX WebView. Не называть клиентский PIN/пароль самостоятельной защитой. Если этот способ не проходит проверку безопасности/совместимости, остановиться и описать ограничение, не подменять его фиктивной авторизацией.

## Структура данных Git-only

Предлагаемая схема (создавать после инвентаризации существующих данных):
- `remont-master-site/data/site.json` — профиль, регион, контакты, тексты и настройки.
- `remont-master-site/data/catalog.json` — позиции каталога и цены.
- `remont-master-site/data/portfolio.json` — материалы четырёх галерей.
- `remont-master-site/data/posts.json` — статьи, новости, объявления и публикации.
- `remont-master-site/assets/uploads/` — изображения и обложки.
- Видео не загружать: хранить URL Rutube и метаданные; встроенный плеер проверять в MAX Mini App, полноэкранный режим и fallback при запрете embed.

Четыре фиксированные категории портфолио:
1. `decorative-walls` — Декоративные стены.
2. `tile` — Плитка и керамогранит.
3. `concrete` — Архитектурный бетон.
4. `complex-structures` — Сложные конструкции.
Не создавать пятую категорию или блок материалов без категории.

## Единый интерфейс администрирования

- Один экран/сайт с переключателем «Просмотр сайта» / «Режим редактирования».
- Контекстные действия у редактируемых элементов: фото, видео, подписи, категории, цены, профиль, регион.
- Одна кнопка «Добавить материал»: изображение или видео-ссылка Rutube.
- Посты: статьи, новости, объявления; черновик/публикация, дата, обложка, редактирование/удаление, закрепление объявлений.
- Колокольчик новостей с красной точкой; прочитанное хранится локально на устройстве/в браузере (не синхронизируется между устройствами без сервера).
- Обычные посетители не видят элементы администрирования.

## Панель «Хранилище и статистика»

Раздельно показывать:
- размер Git-репозитория и историю;
- размер файлов сайта, изображений и данных;
- размер опубликованной Pages-сборки и остаток до лимита Pages 1 ГБ;
- трафик Pages, если GitHub предоставляет фактические данные;
- Actions artifacts и cache — отдельно от файлов сайта;
- статус последней публикации, рост, крупные файлы и предупреждения.

Не выдумывать «остаток» для Git-репозитория: у него нет простого жёсткого лимита как у Pages. Фактические данные отделять от оценок и рекомендаций. APK-артефакты хранить ограниченно; это не срок хранения сайта.

## MAX Mini App

- Сайт должен оставаться доступным в MAX в России без VPN.
- Видео — встроенный Rutube-плеер, не загрузка файла в GitHub.
- Колокольчик внутри сайта реализуем независимо от системного значка MAX.
- Возможность закрепить Mini App как отдельную иконку Android и менять badge проверять по официальному MAX Bridge; не обещать неподтверждённый API.

## Этапы работ

1. Инвентаризация всего текущего содержимого, Worker API, медиа и маршрутов сайта; сохранить резервную копию данных.
2. Исправить и подтвердить деплой GitHub Pages на отдельной ветке/без риска для текущей публикации.
3. Перенести Worker content/catalog/media в Git-файлы, подключить статическое чтение; сравнить публичную версию с текущей.
4. Реализовать админку и безопасную GitHub-запись, формы и загрузку изображений.
   До этого инвентаризировать/перенести также категории, DIY-материалы, блок архитектурного бетона и заявки; для аналитики решить, что возможно без внешнего сервера и что будет честно обозначено как недоступное.
5. Реализовать видео Rutube, четыре галереи, статьи/новости/объявления и колокольчик.
6. Реализовать статистику хранилища.
7. Создать отдельный Android admin-app и workflow APK.
8. Проверить MAX, адаптивность, ссылки, каталог, формы, галереи, авторизацию и публикацию; только затем переключать Pages.

## Правила выпуска

- Ни один шаг не удаляет Worker/старые данные до подтверждения переноса.
- Не менять публичную ветку без успешного теста.
- Не заявлять, что функция готова, пока она не собрана и не проверена.
- Каждый этап — отдельный небольшой commit с проверяемым результатом.
